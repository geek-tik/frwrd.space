Сервис обратного туннелирования для разработчиков: интуитивный проброс локального порта в публичный HTTPS-URL.

---

## Что такое reverse tunnel gateway по сути

Это **не просто «проброс порта»**. Это связка из трёх частей:

```
Интернет → облачный шлюз (публичный URL) → зашифрованный туннель → локальный агент на машине разработчика → localhost:порт
```

Ключевой момент: **агент на машине разработчика сам инициирует исходящее соединение** (обычно на порт 443). Входящие порты на роутере открывать не нужно. Это главная ценность для разработчиков за NAT, в офисе, на домашнем интернете.

---

## Какой трафик обычно пробрасывают такие сервисы

| Протокол | Пример команды (Forward) | Типичные кейсы |
|----------|--------------------------|----------------|
| **HTTP/HTTPS** | `forward http 3000` | Веб-приложения, REST API, webhooks |
| **TCP** | (roadmap) | PostgreSQL, SSH, RDP, игровые серверы, MQTT |
| **TLS** | (roadmap) | TLS passthrough (свой сертификат, без терминации на шлюзе) |
| **UDP** | — | Обычно не поддерживается |

Для HTTP шлюз выдаёт HTTPS-сертификат на публичный URL. Для TCP — публичный `host:port`, часто фиксированный (платно / по резервации).

## Что важно знать о категории продукта

### 1. Туннель — ядро, вокруг него может вырасти платформа

Зрелые продукты расширяются в сторону API gateway, device gateway, identity-aware proxy, site-to-site. Для MVP достаточно туннелей.

### 2. Два типа endpoint'ов (ориентир на будущее)

- **Agent Endpoint** — живёт, пока запущен CLI-агент (локальная разработка).
- **Cloud Endpoint** — постоянный, настраивается в dashboard/API, маршрутизирует на сервисы, даже если агент офлайн.

### 3. Traffic Policy

На туннель можно навесить правила: OAuth, IP whitelist, rate limiting, переписывание заголовков, редиректы, кастомные ответы — без изменения локального кода.

### 4. Инспектор трафика

В веб-интерфейсе видны все HTTP-запросы/ответы, можно **повторить запрос** (replay). Для отладки webhooks это killer feature.

### 5. Стабильные домены и кастомные домены

Бесплатно — случайный URL при каждом запуске. Платно — фиксированный поддомен, свой домен, wildcard.

### 6. Не только «показать localhost коллеге»

В зрелых продуктах бывают Kubernetes Ingress, SDK, config-as-code, team management, SSO, audit log.

### 7. Ограничения бесплатного плана

Лимиты на соединения, bandwidth, количество туннелей, interstitial-страницы перед сайтом — типичный способ толкать к платным планам. Forward сознательно без interstitial.

## Кейсы, которые закрывает продукт

### Основные (80% использования)

1. **Локальная разработка** — показать фронт/бэкенд коллеге или клиенту
2. **Webhooks** — Stripe, GitHub, Telegram, ЮKassa и т.д. шлют callback на localhost
3. **OAuth / SSO callbacks** — redirect URI на локальный сервер
4. **Мобильная разработка** — телефон ходит на API на ноутбуке
5. **Демо и превью** — «вот ссылка, посмотри»

### Средние

6. **Интеграционное тестирование** — внешний сервис стучится в ваш mock
7. **Удалённый доступ к dev-базе** — TCP-туннель к PostgreSQL/Redis
8. **IoT / edge-устройства** — агент на устройстве в поле

### Продвинутые (платформа, не MVP)

9. API Gateway с auth и rate limiting
10. Site-to-site connectivity
11. Device fleet management
12. Ingress в Kubernetes

## Можно ли обойтись только веб-UI?

**Короткий ответ: нет, только веб-UI недостаточно.**

Туннель должен терминироваться **на машине, где крутится сервис**. Браузер не может открыть соединение к `localhost:3000` на ноутбуке разработчика — для этого нужен **локальный агент** (CLI, демон, desktop app).

```
┌─────────────────────────────────────────────────────────┐
│  ОБЯЗАТЕЛЬНО на машине разработчика                     │
│  ┌──────────────┐    outbound TLS    ┌───────────────┐  │
│  │ localhost    │ ◄──────────────── │  Агент        │  │
│  │ :3000        │                    │  (CLI/daemon) │  │
│  └──────────────┘                    └───────┬───────┘  │
└────────────────────────────────────────────┼──────────┘
                                             │
                                    ┌────────▼────────┐
                                    │  Облако (шлюз)  │
                                    │  публичный URL  │
                                    └────────┬────────┘
                                             │
                                    ┌────────▼────────┐
                                    │  Интернет       │
                                    └─────────────────┘

┌─────────────────────────────────────────────────────────┐
│  ВЕБ-UI — для управления и наблюдения                   │
│  • регистрация / биллинг                                │
│  • список туннелей (статус, URL)                        │
│  • инспектор запросов                                   │
│  • настройка доменов, auth, лимитов                     │
│  • API keys / токены для агента                         │
└─────────────────────────────────────────────────────────┘
```

### Рекомендуемая модель взаимодействия

| Слой | Роль | Пример |
|------|------|--------|
| **CLI / агент** | Создать туннель за 1 команду | `forward http 3000` |
| **Веб-UI** | Управление, инспекция, настройки | frwrd.space |
| **API** | Автоматизация, CI/CD | `POST /tunnels` |

### Как сделать продукт удобным без потери мощности

**Уровень 0 — «магия за 30 секунд»:**

```bash
# установка
curl -sSL https://frwrd.space/install | sh

# один токен из веб-UI
forward auth <token>

# один туннель
forward http 3000
# → https://abc123.frwrd.space
```

**Уровень 1 — веб-UI как «пульт»:**

- QR-код / кнопка «Скопировать команду установки»
- Wizard: «Какой порт?» → «Какой протокол?» → готовая команда
- Live-статус туннелей, инспектор HTTP

**Уровень 2 — для продвинутых:**

- `forward.yml` config-as-code
- SDK
- GitHub Action / GitLab CI

**Важно:** веб-UI не заменяет CLI, а **снижает порог входа** и даёт visibility. Модель категории: CLI — ядро, dashboard — ценность поверх.

## Ключевые принципы продукта Forward

### 1. «Одна команда — публичная ссылка»

```bash
forward http 3000
```

Всё остальное — опционально. Если за 60 секунд не получилось — продукт проиграл.

### 2. Агент обязателен, UI — усилитель

CLI/daemon — ядро. Веб — onboarding, мониторинг, биллинг, инспектор.

### 3. HTTP first, TCP second

Сначала HTTP/HTTPS (90% кейсов разработчиков). TCP — во второй фазе.

### 4. Инспектор трафика — must have для HTTP

Просмотр запросов, replay, фильтры — сильный повод платить за продукт.

### 5. Без interstitial перед сайтом

Не показывать промежуточную страницу «нажмите, чтобы открыть» на публичном URL туннеля.

### 6. Русский by default

Документация, ошибки CLI, UI, поддержка — на русском. Английский — опционально.

### 7. Инфраструктура в России

Серверы в РФ, минимальная задержка, соответствие 152-ФЗ, оплата в рублях.

### 8. Прозрачная модель ценообразования

Бесплатно: N туннелей, случайные URL. Платно: фиксированный поддомен, кастомный домен, TCP, team features.

### 9. Безопасность по умолчанию

HTTPS everywhere, токены с ограниченным scope, опциональный basic auth / IP whitelist на туннель.

### 10. Self-hosted как опция (позже)

Для enterprise — свой инстанс. Не в MVP, но в roadmap.

## MVP vs roadmap

### MVP — реализовано (frwrd.space)

- CLI-агент в Docker
- HTTP/HTTPS туннели
- Регистрация + API token
- Случайные поддомены `*.frwrd.space`
- Веб-UI: туннели + HTTP request inspector
- TLS через nginx + Let's Encrypt (DNS wildcard)

### v1.1

- Фиксированные поддомены (платно)
- Basic auth на туннель
- TCP туннели

### v2

- Кастомные домены
- Team / организации
- Config file
- SDK
