# Что мы строим

Forward — сервис обратного туннелирования для разработчиков.

Одна задача: **получить публичный HTTPS-URL на локальный порт** без открытия входящих портов на роутере.

```bash
forward http 3000
# → https://<subdomain>.frwrd.space
```

Агент на машине разработчика устанавливает исходящее соединение к облачному шлюзу. Типичные сценарии: webhooks, демонстрация локального сервиса, OAuth callbacks — без настройки NAT.

В репозитории уже есть рабочий MVP: его можно запустить в первую неделю.
Цель команды за примерно 6 недель — заметно улучшить удобство и надёжность, добавить осмысленные возможности сверх MVP, подготовить публичный запуск и получить опыт командной разработки.

---

# Для кого

Разработчики и небольшие команды, которым нужно быстро открыть localhost для внешнего доступа или принять webhook на локальный сервис.

Главный сценарий:

1. зарегистрироваться на https://frwrd.space;
2. создать API token;
3. запустить локальный сервис на порту;
4. запустить агент (`forward http <port>` или через Docker);
5. открыть выданный URL или направлять на него webhooks;
6. при необходимости просматривать запросы в инспекторе на dashboard.

Критерий качества: шаги 3–5 с нуля укладываются примерно в минуту.

# Структура продукта

- **Server** (`cmd/server`, `internal/`) — REST API, маршрутизация публичных туннелей (edge), WebSocket для агента, аутентификация.
- **Agent / CLI** (`cmd/forward`, `internal/agent*`) — клиент туннеля на стороне разработчика.
- **Dashboard** (`web/`) — регистрация, токены, список туннелей, инспектор HTTP-запросов.
- **Deploy** (`deploy/`, `docker-compose.yml`) — Docker Compose, host nginx, wildcard TLS.

Домен: **frwrd.space**. Поддомены: `api.` (API), `connect.` (агент), `*.` (публичные туннели).

Архив проектирования: [RESEARCH.md](../RESEARCH.md), [MVP_PLAN.md](../MVP_PLAN.md). Эксплуатация: [README.md](../README.md).

# Что уже есть (базовый MVP)

- регистрация, JWT, API tokens;
- HTTP(S)-туннели, случайные поддомены `*.frwrd.space`;
- агент (в том числе через Docker Compose);
- dashboard и инспектор запросов;
- деплой: Compose, nginx, Let's Encrypt (DNS wildcard).

Задача этапа — развивать существующий MVP, а не переписывать его с нуля: улучшить продукт так, чтобы им было удобно пользоваться команде и чтобы его можно было открыть для пользователей. До публичной регистрации доступ к dashboard и API можно ограничить basic auth на nginx (см. [deploy/SERVER_SETUP.md](../deploy/SERVER_SETUP.md)).

# Принципы проекта

- Одна понятная пользовательская задача; остальное — по необходимости.
- CLI и агент — основа продукта; веб-интерфейс помогает с onboarding и отладкой, но не заменяет агент.
- Сначала HTTP; TCP и расширенная платформа — позже.
- На публичном URL туннеля не показывать промежуточную страницу перед сайтом пользователя.
- Интерфейс, сообщения об ошибках и документация — на русском по умолчанию.
- На сервере порты приложения слушают только localhost; снаружи — nginx.
- Изменения через git и небольшие Pull Request; Code Review обязателен.
- Документация отражает принятые решения; этот файл правим вместе.

---

# Вне scope (пока)

- фиксированные и кастомные домены;
- basic auth и IP whitelist на сам туннель (это не то же самое, что pre-launch basic auth на dashboard/API);
- TCP и UDP туннели;
- команды, SSO, биллинг;
- отдельная self-hosted enterprise-сборка;
- SDK и config-as-code (`forward.yml`).

Отдельные пункты можно взять в работу в течение 6 недель, если команда согласует приоритет (например поддержка нескольких портов или basic auth на туннель). Остальное — после публичного запуска.

# Примерная дорожная карта

План можно менять. Старт — с работающего продукта: сначала проходим основной сценарий, фиксируем замечания, за 6 недель улучшаем качество и возможности.

### Неделя 1 — Знакомство с Vision и правилами работы; у каждого участника запущен продукт и пройден главный сценарий; собран общий список замечаний

- знакомство команды, Vision, правила PR и Code Review;
- у каждого участника: локальный или стендовый запуск по README и проверка главного сценария;
- общий список замечаний и идей после первого использования.

### Неделя 2 — Согласованы 1–2 крупные задачи этапа и набор мелких исправлений; архитектура разобрана достаточно для самостоятельных задач; есть первые merged PR и критерии готовности

- обзор архитектуры в объёме, достаточном для самостоятельных задач;
- выбор 1–2 крупных задач на этап (например несколько портов, UX инспектора, удобство агента) и набор небольших исправлений;
- первые merged PR; критерии готовности для крупных задач.

### Неделя 3 — Приоритетная задача №1 доведена до демонстрации; упрощены onboarding и сообщения об ошибках; главный сценарий не сломан

- реализация приоритетной задачи №1 до состояния, пригодного для демонстрации;
- параллельно: упрощение onboarding (токен → запуск → URL) и понятные сообщения об ошибках;
- основной сценарий остаётся рабочим (чеклист проверки).

### Неделя 4 — Сделана приоритетная задача №2 или углублена №1; принят сценарий webhook или демо по публичному URL; добавлены тесты или регрессионный чеклист по найденным дефектам

- приоритетная задача №2 или углубление задачи №1 (переподключение агента, инспектор, dashboard);
- приёмка: сценарий webhook или демонстрация по публичному URL;
- тесты или регрессионный чеклист там, где уже находили дефекты.

### Неделя 5 — Доработан UX сквозного сценария; проверена устойчивость к обрывам и перезапускам; документация совпадает с актуальным процессом запуска

- доработка UX по всему сценарию;
- устойчивость: обрыв сети, перезапуск агента, несколько туннелей у одного пользователя;
- документация и команды запуска соответствуют актуальному процессу.

### Неделя 6 — Закрыты хвосты; показаны изменения за этап; принято решение по публичному запуску; проведена ретроспектива

- закрытие оставшихся задач, демонстрация изменений за этап;
- решение по публичному запуску (стенд, снятие или сохранение basic auth на dashboard/API);
- ретроспектива: что вошло в продукт, что переносится дальше.

При необходимости этап можно продлить на 1–2 недели. Целевой ориентир — к 6-й неделе видимое улучшение MVP относительно старта.
