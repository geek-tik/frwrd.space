# Участие в разработке Forward

Спасибо, что участвуете в проекте.

## Перед началом

1. Ознакомьтесь с [vision](docs/vision.md) и [README](README.md).
2. Согласуйте задачу с командой, чтобы не дублировать работу.

## Стиль кода

- Следуйте соглашениям, уже принятым в соответствующей части репозитория (Go / TypeScript / Docker).
- Не смешивайте несвязанные изменения в одном PR.
- Не делайте массовый reformat «заодно».

## Вопросы

Если что-то неясно — спросите в общем чате команды или в комментариях к issue/PR.

## Архитектура

- **Server** (`cmd/server`, `internal/`) — REST API, edge (публичные туннели), WebSocket для агента, auth.
- **Agent / CLI** (`cmd/forward`, `internal/agent*`) — исходящий туннель с машины разработчика.
- **Dashboard** (`web/`) — UI: регистрация, токены, туннели, инспектор запросов.
- **Deploy** (`deploy/`, `docker-compose.yml`, `migrations/`) — контейнеры, nginx, миграции БД.

Локальный запуск: [README](README.md). Прод: [deploy/SERVER_SETUP.md](deploy/SERVER_SETUP.md).

## Быстрый старт (первый PR)

1. Возьмите задачу из **To Do** и перенесите в **In Progress**.
2. Ветка от `main`: `feature/…` или `fix/…`.
3. Коммиты: `feat: …`, `fix: …` (см. п. 3.2).
4. PR в `main` со ссылкой на карточку задачи.
5. Карточка → **Ready for Review**.
6. Следующую задачу можно брать; merge в `main` делает ревьюер после проверки.

## Полный процесс: задачи и Git

### 1. Базовые правила

1.0. Цель — уменьшать объём незавершённой работы: сначала доводим то, что ближе к Done. В **In Progress** стараемся держать одну свою задачу.

1.1. У задачи в In Progress должен быть исполнитель.

1.2. Стабильная ветка: `main`.

1.3. Путь: `main` → ветка → pull request → `main`.

1.4. Освободились — следующая задача из назначенных в To Do.

1.5. В To Do пусто — уточните в чате команды.

1.6. Не берём задачи с лейблом `Требует уточнения` или с незакрытой зависимостью.

### 2. Ветки

2.1. Одна задача — одна ветка.

2.2. Имя: `feature/краткое-описание` или `fix/краткое-описание`.

2.3. От `main`:

```bash
git checkout main && git pull origin main && git checkout -b <my-feature-branch>
```

2.4. Название ветки указываем в карточке задачи.

### 3. Коммиты

3.1. Формат: `<type>: <краткое описание>`.

3.2. `type`: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`.

3.3. Force push (`--force`, `--force-with-lease`) — только если понимаете последствия.

### 4. Перед Ready for Review

4.1. Подтянуть `main` в свою ветку:

```bash
git checkout <my-feature-branch> && git pull origin main
```

4.2. `git push origin <my-feature-branch>`.

4.3. PR в `main`; заголовок — ветка или название задачи.

4.4. В PR — ссылка на карточку; в карточке — ссылка на PR.

4.5. В карточке — минимальные шаги проверки (CLI / dashboard / туннель — по сути задачи).

4.6. Если проверки у автора не проходят — на ревью не отдаём.

4.7. Конфликты с `main` по возможности закрываем сами (п. 4.1); иначе — комментарий в карточке.

4.8. Карточка → **Ready for Review**.

### 5. Testing

5.0. В Testing переносит ревьюер.

5.1. Пока задача в Testing и нет запросов на правки — новые коммиты не пушим (в т.ч. из‑за свежих конфликтов на GitHub); конфликты в этом статусе закрывает ревьюер.

5.2. Правки — по п. 6.1.

### 6. Итог ревью

6.1. Нужны доработки — комментарий, статус **Need to Fix**; после правок снова **Ready for Review**. Перед доработкой карточку вернуть в **In Progress**.

6.2. Готово — **Done**, ревьюер одобряет PR и мержит в `main`.

6.3. Приоритет своих карточек (справа налево): Need to Fix → Ready for Review (если вы ревьюер) → In Progress → To Do.
